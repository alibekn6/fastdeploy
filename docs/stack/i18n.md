# next-intl

**Version:** 4.13.0 (dependency)

## What & why

next-intl provides typed internationalization for the App Router: locale routing, request-scoped message loading, and `useTranslations`/`getTranslations` for server and client components. This repo serves three locales — English, Russian, Kazakh — under a single `app/[locale]` segment, with the message catalog kept out of source files so UI strings stay translatable.

## Conventions / rules

### Routing — `src/shared/i18n/routing.ts`

```ts
export const routing = defineRouting({
  locales: ["en", "ru", "kk"],
  defaultLocale: "en",
  localePrefix: "as-needed",
});
```

- Locales: `en`, `ru`, `kk`. `kk` is **Kazakh** (BCP-47), **not** `kz`.
- `localePrefix: "as-needed"` — the default locale (`en`) is served unprefixed (`/`, `/login`); other locales are prefixed (`/ru`, `/kk/dashboard`).

### Module map (`src/shared/i18n/`)

- `routing.ts` — `defineRouting`, the single source of locales/default/prefix.
- `request.ts` — `getRequestConfig`: resolves `requestLocale`, falls back via `hasLocale`, and lazy-imports `../../../messages/${locale}.json`.
- `navigation.ts` — `createNavigation(routing)` exports locale-aware `Link`, `redirect`, `usePathname`, `useRouter`, `getPathname`.
- `index.ts` — the slice's public API (named re-exports of routing + navigation).

### Wiring

- `next.config.ts` wraps the config with `createNextIntlPlugin("./src/shared/i18n/request.ts")` (`withNextIntl`).
- `global.d.ts` augments next-intl's `AppConfig` with `Locale` (from `routing.locales`) and `Messages` (from `messages/en.json`) → typed translation keys.
- `messages/{en,ru,kk}.json` — keep all three in sync; `en.json` is the typing source.
- `proxy.ts` (root middleware) runs the **cookie auth gate first** — it strips a leading `/ru|/kk` to normalize the path, presence-checks `SESSION_COOKIE` for `/dashboard`, then hands off to `createMiddleware(routing)` for locale routing. The matcher is **site-wide**: `"/((?!api|_next|_vercel|.*\\..*).*)"`.

### Pages and layouts (`app/[locale]/`)

Every page/layout: `const { locale } = await params;` → `if (!hasLocale(routing.locales, locale)) notFound();` → `setRequestLocale(locale)`. Metadata uses `getTranslations({ locale, namespace })` so it stays static.

## ✅ Best practices

- `await params` — in Next 16 `params` is a Promise.
- Call `setRequestLocale(locale)` in every static layout/page **before** any translation call; otherwise next-intl silently forces dynamic rendering.
- In `generateMetadata`, pass an explicit `{ locale }` to `getTranslations` to keep the route static.
- Keep messages typed via the `global.d.ts` `AppConfig` augmentation.
- Use `useTranslations` (client) / `getTranslations` (server) — never hardcode UI strings.
- Navigate with `Link`/`useRouter` from `@/shared/i18n`, not `next/link` (they handle the locale prefix).
- Keep the i18n middleware matcher site-wide so locale routing covers every page.

## ❌ Worst practices / anti-patterns

- Forgetting `await params` (you get a Promise, not the locale).
- Omitting `setRequestLocale` — silently opts the route into dynamic rendering.
- A narrow middleware matcher — skips locale routing on uncovered paths.
- Shipping the whole message catalog to every client component.
- Hardcoded UI strings instead of translation keys.
- Using `kz` instead of `kk` for Kazakh.
